## 39장 - 한국어 키워드 검색과 형태소 분석

- 키워드 검색은 **단어가 그대로 일치**해야 찾는다. 대표적인 방식이 BM25.
- 한국어는 단어 뒤에 조사·어미가 붙는다. 띄어쓰기로만 자르면 "휴학은", "휴학을", "휴학이"가 모두 다른 단어가 되어, "휴학"으로 검색해도 못 찾는 일이 생긴다.
- 그래서 한국어 키워드 검색은 **형태소 분석**으로 "휴학 + 은"처럼 쪼갠 뒤 색인한다.
  - 예: Elasticsearch·OpenSearch의 한국어 분석기 nori, Python의 Kiwi(kiwipiepy)·KoNLPy
- 하이브리드 검색에서 두 결과를 합칠 때는 각 검색의 순위를 합산하는 방식(예: RRF, Reciprocal Rank Fusion)을 많이 쓴다.
- 의미 검색이 조항 번호를 늘 놓치는 것은 아니다. 슬라이드에도 "✕"가 아니라 "△ 놓칠 수 있음"으로 적었다.
- 한국어 임베딩 모델 고르기는 `notes/part2-embedding-model.md`(MTEB 한국어 리더보드) 참고.

## 40장 - 결과 선별 보충

- 슬라이드 순서는 원고(리랭킹 → 메타데이터 → Top-k)가 아니라 실제 처리 순서(범위 좁히기 → 1차 검색 → 다시 줄 세우기 → 자르기)대로 놓았다.
- 리랭킹 모델은 질문과 후보를 한 쌍씩 함께 읽고 점수를 매긴다(흔히 cross-encoder라고 부름). 정밀하지만 느려서, 전체 문서가 아니라 1차 검색으로 추린 후보에만 쓴다.
- "후보 20개", "2026학년도"는 이해를 돕기 위한 예시.
- 단원 마지막 메시지: 답이 이상하면 프롬프트를 고치기 전에, 어떤 조각이 검색됐는지부터 확인한다.

## 자주 나올 질문 (제작 중 나온 질문과 답)

### Top-k는 정해진 숫자인가?
- 아니다. **개발자가 정하는 설정값**이다. 34·40장의 "2개"는 예시.
  ```python
  chunks = vector_db.search(q_vec, top_k=2)   # 이 숫자를 개발자가 정한다
  ```
- 정답이 있는 숫자가 아니라서, 예상 질문 여러 개로 k를 바꿔 가며 "정답 조각이 들어오는지 / 쓸데없는 조각이 섞이는지"를 비교해 고른다.
- 개수 대신 "유사도 점수가 일정 이상인 것만"으로 자르는 방식도 있다.

### 메타데이터 필터, 1차 검색, 리랭킹도 개발자가 코드로 쓰나?
- 어떤 단계를 어떤 순서로 쓸지는 **개발자가 정하고 코드로 조립**한다. 각 기능은 이미 있는 도구를 불러 쓴다.
  ```python
  candidates = vector_db.search(q_vec, top_k=20, filter={"학년도": 2026})  # 메타데이터 필터 + 1차 검색 (벡터 DB 기능)
  ranked = reranker.rank(question, candidates)                             # 리랭킹 (전용 모델·API)
  chunks = ranked[:2]                                                      # Top-k
  ```
- 메타데이터 필터를 쓰려면 **준비 단계에서 조각마다 학년도·버전 같은 정보를 붙여 저장**해 둬야 한다. 이것도 개발자의 일.
- 리랭킹 모델 예: Voyage AI `rerank-2.5`(Claude 공식 문서에 소개), 공개 cross-encoder 모델.
- LangChain, LlamaIndex 같은 프레임워크를 쓰면 조립이 짧아지지만, 무엇을 넣을지는 여전히 개발자가 정한다.

### 키워드 검색도 임베딩 모델을 쓰나?
- **안 쓴다.** 두 방식은 엔진 자체가 다르다. (39장 머리글에 "임베딩 / 단어 일치"로 표시)

| | 의미 검색 | 키워드 검색 |
|---|---|---|
| 쓰는 것 | 임베딩 모델 + 벡터 DB | 글 그대로 |
| 점수 | 숫자 목록끼리 얼마나 가까운가 | 질문 단어가 몇 번 나오나, 얼마나 드문 단어인가 (BM25) |
| 준비 | 조각마다 숫자 목록 저장 | 단어 → 나오는 조각 목록 색인표 (책 뒤 찾아보기와 같은 원리) |

- 키워드 검색 = **풀텍스트 서치(full-text search)**. 대표 엔진이 Elasticsearch·OpenSearch(기본 점수 방식 BM25).
- SQL `LIKE '%휴학%'`과 다른 점: `LIKE`는 들어 있다/없다만 걸러내고 모든 행을 훑는다. 키워드 검색은 미리 만든 색인으로 찾고 **관련도 순위**를 매긴다.
  - 예: "제13조 복학 신청" → 드문 단어("제13조", "복학")가 있는 제13조가, 흔한 단어("신청")만 있는 제5조(수강신청)보다 위로 온다.
- SQL DB의 풀텍스트 기능: PostgreSQL `tsvector`·`ts_rank`, MySQL `FULLTEXT` + `MATCH … AGAINST`. 한국어는 조사 때문에 n-gram 파서나 형태소 분석기(nori 등) 설정이 필요하다.
- 의미 검색도 PostgreSQL 확장 pgvector로 SQL 안에서 할 수 있고, Elasticsearch·OpenSearch도 벡터 검색을 지원한다. 그래서 엔진 하나에서 하이브리드 검색을 돌리는 구성이 흔하다.

### 하이브리드 검색은 질문마다 어느 쪽을 쓸지 고르나?
- **고르지 않는다.** 두 검색을 매번 같이 돌리고 결과를 합친다.
  ```
  질문 ─┬─ 의미 검색 → 후보 20개 (순위 목록 A)
        └─ 키워드 검색 → 후보 20개 (순위 목록 B)
                   ↓
             두 목록 합치기 (보통 RRF)
                   ↓
             (선택) 리랭킹 → Top-k
  ```
- 두 검색은 점수 단위가 달라(BM25는 12.4처럼 크게, 유사도는 0~1) 그대로 더할 수 없다. 그래서 RRF(Reciprocal Rank Fusion)는 **점수 대신 순위만** 쓴다. 각 목록에서 `1 / (60 + 순위)`를 구해 더하므로(60은 흔히 쓰는 상수), **두 목록 모두에서 위쪽에 있는 조각**이 올라온다.
- 예: "제13조 내용 알려줘" (순위는 예시)

| 조항 | 의미 검색 | 키워드 검색 | 합산 |
|---|---|---|---|
| 제13조 | 3위 | 1위 | 1/63 + 1/61 ≈ **0.0323** |
| 제12조 | 1위 | 5위 | 1/61 + 1/65 ≈ 0.0318 |
| 제5조 | 2위 | 없음 | 1/62 ≈ 0.0161 |

  → 의미 검색이 제13조를 3위로 놓쳐도 키워드 검색이 1위로 올려 최종 1위가 된다.
- 합치기와 리랭킹은 다른 단계다. RRF는 AI가 아니라 코드 속 계산식(빠르고 공짜), 리랭킹은 질문과 후보를 한 쌍씩 읽는 모델(정밀하지만 느림)이다. 흔히 "하이브리드로 합친 후보 20개 → 리랭킹 → Top-k" 순서로 쓴다. 40장의 "1차 검색" 자리에 하이브리드 검색이 들어간다고 보면 된다.
- 질문에 "제○조" 같은 패턴이 있으면 키워드 쪽 비중을 높이거나, LLM이 질문을 보고 검색 방식을 정하는 구성(질의 라우팅)도 있다. 하지만 기본은 "둘 다 돌리고 합치기". 판단이 틀릴 위험이 없고 단순하다.

### 청킹은 결국 운에 맡기는 것 아닌가?
- 개발자가 조각을 하나씩 확인하지는 않지만, 운도 아니다. **규칙으로 나누고 → 맥락을 보태고 → 시험해서 고치는** 반복 작업이다.
  1. **구조 규칙으로 자동 분할**: 규정은 "제○조"마다, 마크다운은 `#` 제목마다, 그 밖에는 빈 줄(문단)마다. 구조가 뚜렷한 문서는 대부분 이걸로 해결된다.
  2. **크기 상한과 단계별 분할**: 너무 긴 조각은 제목 → 문단 → 문장 순으로 더 나누고, 경계는 오버랩으로 보완한다.
  3. **조각에 맥락 붙이기**: 조각 앞에 "Kant 대학교 학사 규정 > 제13조 (복학)"처럼 문서 제목·위치를 붙여 저장한다. 발전된 방법으로 Anthropic의 Contextual Retrieval(LLM이 조각마다 짧은 설명을 붙임), Voyage AI의 문맥 반영 임베딩 모델(voyage-context)이 있다.
  4. **시험으로 확인**: 예상 질문 목록으로 정답 조각이 검색되는지 돌려 보고, 나쁘면 규칙·크기를 바꿔 다시 돌린다.
- 모든 문서에 맞는 정답 크기는 없어서, 문서 종류마다 맞춰 가야 한다.

### 청킹이 잘 됐는지는 어떻게 확인하나?
- 답변을 몇 번 읽어 보고 고르는 게 아니라, **정답이 있는 시험지로 점수를 매긴다.**
1. **평가용 질문 세트**: 질문마다 정답 조각과 모범 답을 붙인다. 수십~100개로 시작. LLM에게 조각을 주고 예상 질문을 만들게 한 뒤 사람이 걸러 내면 빨리 만들 수 있다.

| 질문 종류 | 예 | 확인하려는 것 |
|---|---|---|
| 표현이 다른 질문 | "학교 잠시 쉬고 싶은데 얼마나 돼?" → 제12조 | 의미 검색 |
| 정확한 단어 | "제13조 내용 알려줘" → 제13조 | 키워드 검색 |
| 여러 조항이 필요한 질문 | "휴학하고 복학 안 하면?" → 제12·13조 | 청크 경계, k |
| 문서에 없는 질문 | "기숙사 신청은 언제야?" → 없음 | "모른다"고 답하는지 |

2. **검색과 답변을 따로 채점**

| 대상 | 지표 | 뜻 |
|---|---|---|
| 검색 | Recall@k (적중률) | 정답 조각이 상위 k개 안에 들어왔나 |
| | MRR | 정답 조각이 몇 번째로 나왔나 (위일수록 좋음) |
| 답변 | 근거성 (faithfulness) | 검색된 조각에 있는 내용만 말했나 (환각 여부) |
| | 정확성 | 모범 답과 내용이 맞나 |

  - 청킹·검색 방식·k·하이브리드 비중을 고르는 기준은 주로 **검색 점수**.
  - 답변 채점은 LLM이 채점하고(LLM-as-a-judge) 사람이 일부 확인한다. RAGAS 같은 평가 도구가 이런 지표를 제공한다.
3. **한 번에 하나만 바꿔 비교**: 여러 값을 한꺼번에 바꾸면 무엇 때문에 좋아졌는지 알 수 없다.
4. **틀렸을 때 원인 나누기** (40장 결론과 같은 이야기)

| 상황 | 원인 | 고칠 곳 |
|---|---|---|
| 정답 조각이 검색되지 않음 | 검색 문제 | 청킹, 검색 방식, 임베딩 모델, k |
| 정답 조각이 왔는데 답이 틀림 | 생성 문제 | 프롬프트, 모델 |

5. **서비스 중에도 계속**: 질문마다 검색된 조각을 로그로 남기고, 사용자 피드백·"모르겠다" 답이 몰리는 질문을 찾는다. 실패한 질문은 시험지에 추가하고, 규정이 바뀌면 시험지를 다시 돌린다. 저장된 조각도 가끔 직접 열어 본다(문장 중간에서 잘렸는지, 폐지된 규정이 남았는지).

### 청킹을 바꾸면 문서를 전부 다시 처리해야 하나?
- 청킹 규칙을 바꾸면 그 규칙을 쓰는 문서는 **다시 청킹 → 임베딩 → 저장**하고 옛 조각은 지운다. 조각이 바뀌면 벡터도 바뀌기 때문.
- 부담은 크지 않다. 준비 단계(31장)는 보통 스크립트 하나라서 값만 바꿔 다시 돌린다. 원본 문서와 PDF에서 뽑은 글은 따로 보관하고, 조각은 언제든 다시 만들 수 있는 결과물로 다룬다. 학사 규정 정도면 몇 초~몇 분이면 끝나고, 문서가 수십만 건이면 바뀐 문서만 다시 하는 방식이 중요해진다.
- 실험할 때는 서비스 중인 DB를 건드리지 않는다. 설정마다 저장 공간을 따로 만들고(예: `규정_조항단위`, `규정_500자`) 평가용 질문 세트로 비교한 뒤, 가장 좋은 것을 서비스에 연결한다.
- 무엇을 바꿨느냐에 따라 범위가 다르다.

| 바꾼 것 | 다시 할 일 | 범위 |
|---|---|---|
| 청킹 규칙 (크기 · 오버랩 · 나누는 기준) | 청킹 → 임베딩 → 저장 | 그 규칙을 쓰는 문서 전체 |
| 문서 하나에만 문제 (표가 깨짐, 조항이 너무 김) | 그 문서만 | 해당 문서의 조각만 지우고 다시 넣기 |
| 규정 개정 (내용 변경) | 그 문서만 | 바뀐 문서만 교체 |
| 임베딩 모델 | 임베딩 → 저장 (조각은 그대로 가능) | **전체** (33장: 문서와 질문은 같은 모델로) |
| k · 하이브리드 비중 · 리랭킹 · 필터 조건 · 프롬프트 | **없음** | 질문 단계 설정이라 바로 바뀜 |

- 문서 하나만 교체하려면 조각마다 문서 ID를 메타데이터로 붙여 저장해 둬야 한다. 문서 내용으로 해시를 만들어 두면 바뀐 문서를 자동으로 찾을 수 있다.
  ```python
  vector_db.delete(filter={"doc_id": "학사규정"})   # 이 문서의 옛 조각만 지우고
  vector_db.add(new_chunks, new_vectors)            # 새 조각을 넣는다
  ```
- 그래서 **다시 만들어야 하는 것**(청킹, 임베딩 모델)은 실험 단계에서 먼저 정하고, **바로 바꿀 수 있는 것**(k, 하이브리드 비중, 리랭킹, 프롬프트)은 서비스하면서 조정한다.
